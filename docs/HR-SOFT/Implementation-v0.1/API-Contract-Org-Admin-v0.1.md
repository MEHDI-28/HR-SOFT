# قرارداد API و اتصال تدریجی رابط مدیریت سازمانی — v0.1

- وضعیت: قرارداد نسخه ۱ مستقر شده است؛ دو RPC خواندنی روی Supabase اصلی منتشر شده‌اند و صفحه فقط‌خواندنی رابط به آن‌ها متصل شده است. آزمون مثبت با نشست واقعی مدیر هنوز باقی است.
- محیط هدف بررسی: Supabase پروژه Org-Ch / HR-SOFT
- دامنه این نسخه: خواندن امن اطلاعات پایه ساختار سازمانی
- خارج از دامنه: ایجاد/ویرایش/حذف، پرسنل و اطلاعات حساس، فایل‌ها، گردش کار و تأیید تغییرات

## 1. وضعیت مبنا و شواهد

- Data API فقط schemaهای `public` و `graphql_public` را expose می‌کند؛ schemaهای `hr_*` خصوصی باقی می‌مانند.
- ۵۷ جدول HR-SOFT دارای RLS و FORCE RLS هستند و داده‌های دامنه به‌صورت پیش‌فرض fail-closed هستند.
- RPC عمومی `hr_session_status()` وضعیت احراز هویت و provision شدن حساب داخلی را برمی‌گرداند.
- دو RPC خواندنی `hr_admin_get_context_v1()` و `hr_org_get_admin_snapshot_v1(...)` منتشر شده‌اند؛ هر دو wrapper عمومی از نوع SECURITY INVOKER هستند و منطق مجوز در schema خصوصی `hr_internal` اجرا می‌شود.
- Permission Resolver از طریق همین RPCها به خواندن مجاز context و snapshot متصل شده است؛ اجرای مستقیم Resolver از مرورگر همچنان مجاز نیست.
- شرکت اولیه `Org-Ch` فعال است؛ جدول‌های `org_layers`، `org_units`، `positions`، `position_relationships` و `organizational_positions` در حال حاضر داده عملیاتی ندارند.
- رابط فعلی `index.html` از `localStorage` استفاده می‌کند. فرم سمت فعلی فیلدهای متعددی دارد که معادل مستقیم و قطعی در مدل نرمال‌شده HR-SOFT ندارند؛ اتصال مستقیم فرم فعلی به جدول `positions` مجاز نیست.
- گروه `tenant_owner` در زمان بررسی ۶۸ قاعده Allow دارد؛ این تعداد به‌تنهایی اثبات‌کننده عملکرد صحیح Resolver نیست.

## 2. اصول امنیتی غیرقابل مذاکره

1. هیچ جدول `hr_*` مستقیماً از مرورگر خوانده یا نوشته نمی‌شود.
2. هیچ شناسه tenant از مرورگر به‌عنوان مرجع مجاز بودن پذیرفته نمی‌شود. Tenant فقط از `auth.uid()` و نگاشت فعال `hr_security.app_users` استخراج می‌شود.
3. `company_id` ورودی احتمالی فقط یک شناسه انتخابی است؛ API باید تعلق آن به tenant جاری، فعال بودن و بازه اعتبارش را در سرور بررسی کند.
4. هر عملیات قبل از خواندن داده با Permission Resolver ارزیابی می‌شود. در این مرحله مجوزهای لازم عبارت‌اند از:
   - `org.company.view`
   - `org.unit.view`
   - `org.position.view`
   - `org.relationship.view`
   - `org.chart.view`
5. تصمیم دسترسی فقط بر اساس قواعد سمت سرور و Resolver است؛ UI صرفاً کنترل‌های نمایشی را پنهان/نمایان می‌کند و مرجع امنیتی نیست.
6. هیچ `service_role` یا Secret Key در مرورگر، فایل‌های tracked یا کد HTML قرار نمی‌گیرد.
7. هر RPC عمومی باید `EXECUTE` را صریحاً از `PUBLIC` و `anon` بگیرد و فقط به `authenticated` داده شود.
8. هر تابع ممتاز باید `search_path = ''` داشته باشد، نام schemaها را کامل بنویسد، ورودی‌ها را validate کند و سطح داده برگشتی را حداقلی نگه دارد.
9. تا وقتی آزمون‌های cross-tenant، deny-overrides-allow، scope و عدم افشای داده موفق نشده‌اند، API عملیاتی به UI وصل نمی‌شود.
10. هیچ Policy باز یا عمومی برای رفع هشدارهای RLS بدون Policy ساخته نمی‌شود.

## 3. الگوی پیشنهادی API

برای فاز اول، RPCهای محدود PostgreSQL در schema عمومی و با نام‌های versioned استفاده می‌شوند. منطق واقعی در schema خصوصی باقی می‌ماند. از آنجا که نقش مرورگر به schema خصوصی و جداول HR دسترسی مستقیم ندارد، wrapper عمومی باید یک مرز امنیتی بسیار کوچک باشد.

### 3.1 `public.hr_admin_get_context_v1()`

- روش: RPC بدون ورودی
- کاربرد: نمایش وضعیت حساب، tenant جاری، فهرست شرکت‌های قابل انتخاب و قابلیت‌های مجاز کاربر
- داده‌های خروجی پیشنهادی:
  - `user`: شناسه داخلی کاربر و وضعیت فعال
  - `tenant`: شناسه و نام tenant جاری
  - `companies[]`: فقط شرکت‌های فعال و معتبر همان tenant که کاربر مجاز به مشاهده آن‌هاست
  - `capabilities`: مقادیر boolean برای مجوزهای نمایش UI
- Tenant و app_user از `auth.uid()` استخراج می‌شوند؛ هیچ ورودی tenant ندارد.
- هر capability از Resolver محاسبه می‌شود؛ فهرست Allow خام یا شناسه گروه‌ها به مرورگر ارسال نمی‌شود.
- اگر نشست معتبر یا app_user فعال نباشد، پاسخ deny/unauthenticated است.

### 3.2 `public.hr_org_get_admin_snapshot_v1(p_company_id uuid, p_effective_at date default current_date)`

- روش: RPC فقط خواندنی
- کاربرد: بارگذاری snapshot ساختار سازمانی برای شرکت انتخاب‌شده در تاریخ مؤثر
- ورودی‌ها:
  - `p_company_id`: شرکت انتخابی؛ در سرور باید به tenant جاری تعلق داشته باشد.
  - `p_effective_at`: تاریخ مؤثر؛ اگر null باشد، تاریخ جاری سرور استفاده شود.
- خروجی پیشنهادی:
  - `company`
  - `org_layers[]`: لایه‌ها با ترتیب نمایش
  - `org_units[]`: واحدها با parent، layer، کد، عنوان، نوع و وضعیت نمایش/فعال
  - `organizational_positions[]`: موقعیت‌های سازمانی با اولویت و سطح
  - `positions[]`: سمت‌ها با واحد، مافوق، عنوان، ظرفیت مصوب و بازه اعتبار
  - `relationships[]`: روابط سازمانی مجاز در بازه مؤثر
  - `meta`: تاریخ مؤثر و نسخه قرارداد
- هر مجموعه با مجوز مرتبط خود کنترل می‌شود. اگر مجوز یک زیرمجموعه وجود نداشته باشد، آن مجموعه خالی/حذف‌شده با قرارداد روشن برگردد؛ نباید از طریق خطای SQL یا داده جانبی اطلاعات افشا شود.
- API فقط رکوردهای tenant و company انتخاب‌شده را برمی‌گرداند.
- رکوردهای archived یا خارج از بازه اعتبار در snapshot جاری نمایش داده نمی‌شوند؛ قابلیت تاریخچه باید در قرارداد جداگانه تعریف شود.
- هیچ داده هویتی، بانکی، تماس خصوصی یا پرونده پرسنلی در این endpoint برگردانده نمی‌شود.

## 4. قرارداد خطا

پاسخ خطا باید ساختار ثابت و بدون جزئیات داخلی SQL داشته باشد:

- `AUTH_REQUIRED`: نشست معتبر وجود ندارد.
- `APP_USER_INACTIVE`: نگاشت کاربر داخلی فعال نیست.
- `PERMISSION_DENIED`: مجوز لازم وجود ندارد یا Resolver دسترسی را رد کرده است.
- `RESOURCE_NOT_FOUND`: شرکت در tenant جاری وجود ندارد یا قابل مشاهده نیست.
- `INVALID_ARGUMENT`: ورودی نامعتبر است.
- `INTERNAL_ERROR`: خطای غیرمنتظره؛ جزئیات فقط در log امن سمت سرور ثبت می‌شود.

برای جلوگیری از افشای وجود شرکت در tenant دیگر، شناسه نامعتبر و شناسه متعلق به tenant دیگر باید پاسخ یکسان `RESOURCE_NOT_FOUND` داشته باشند.

## 5. توالی اتصال رابط

1. `auth.html` مرجع ورود باقی می‌ماند؛ بعد از ورود، `index.html` باید وضعیت نشست را از Supabase دریافت کند.
2. در شروع `index.html`، فقط `hr_admin_get_context_v1()` فراخوانی می‌شود.
3. اگر کاربر احراز هویت نشده یا provision نشده باشد، صفحه به `auth.html` هدایت می‌شود.
4. انتخاب شرکت از خروجی مجاز API ساخته می‌شود؛ UI شناسه شرکت را از فهرست سرور می‌گیرد.
5. پس از انتخاب شرکت، `hr_org_get_admin_snapshot_v1()` فراخوانی می‌شود.
6. تب «ساختار درختی» ابتدا به snapshot خواندنی متصل می‌شود. حالت خالی با پیام «برای این شرکت هنوز ساختار سازمانی ثبت نشده است» نمایش داده می‌شود.
7. تا زمان پیاده‌سازی APIهای نوشتن، دکمه‌های افزودن/ویرایش/حذف و ذخیره Excel نباید وانمود کنند که داده را در پایگاه داده ذخیره می‌کنند. این قابلیت‌ها باید غیرفعال یا صریحاً با برچسب «محلی/آزمایشی» مشخص شوند.
8. بعد از تأیید API خواندنی و تطبیق مدل، فرم‌های ایجاد/ویرایش با عملیات جداگانه و دارای audit متصل می‌شوند.

## 6. عدم تطابق‌های فعلی UI و مدل داده

فرم فعلی `index.html` فیلدهایی مانند «امور/دپارتمان»، «پایه سمت»، «نوع ساختار»، «حداقل/حداکثر گروه»، «شرایط احراز»، «تجربه»، «کد/عنوان بیمه»، «رده هلدینگ»، «رده مدیریت»، «ماهیت شغل» و «تاپ چارت» دارد.

مدل نرمال‌شده فعلی `hr_org.positions` شامل `position_code`، `title`، `org_unit_id`، `superior_position_id`، `approved_capacity`، `organizational_position_id` و تاریخ‌های اعتبار است. این دو مدل معادل یک‌به‌یک نیستند.

بنابراین پیش از اتصال فرم سمت باید نگاشت فیلدها و تصمیم درباره موارد فاقد ستون مشخص شود. نباید اطلاعات فرم قدیمی به ستون نامرتبط یا JSON آزاد منتقل شود.

## 7. آزمون‌های پذیرش پیش از اتصال

- بدون نشست: هر دو RPC رد شوند.
- نشست Auth بدون app_user فعال: رد شود.
- کاربر tenant دیگر: هیچ شناسه یا داده‌ای از tenant دیگر مشاهده نشود.
- شرکت نامعتبر/متعلق به tenant دیگر: پاسخ یکسان `RESOURCE_NOT_FOUND`.
- حذف مجوز `org.company.view`: فهرست شرکت‌ها نمایش داده نشود.
- حذف مجوزهای unit/position/relationship/chart: داده مربوطه برنگردد.
- deny در یک گروه در برابر allow گروه دیگر: رفتار deny-overrides مطابق قرارداد Resolver باشد.
- عضویت منقضی/غیرفعال: دسترسی رد شود.
- scope محدود به شرکت/واحد: داده خارج از scope برنگردد.
- تاریخ مؤثر: فقط رکوردهای معتبر در همان تاریخ نمایش داده شوند.
- مرورگر نتواند با REST مستقیم به schemaهای `hr_*` یا جداول دامنه دسترسی بگیرد.
- پاسخ API هیچ داده حساس پرسنلی را شامل نشود.

## 8. تصمیم‌های تثبیت‌شده و موارد باقی‌مانده

1. انتخاب شرکت در UI چندشرکتی طراحی شده است؛ فقط شرکت‌هایی که capability مشاهده چارت دارند در فهرست انتخاب نمایش داده می‌شوند.
2. سیاست snapshot تثبیت شده است: capabilityها در context و snapshot اعلام می‌شوند و آرایه‌های هر دامنه فقط با مجوز مربوطه و در scope مجاز پر می‌شوند؛ ارجاع به رکورد غیرقابل مشاهده redacted می‌شود.
3. نگاشت فیلدهای legacy فرم سمت به مدل نرمال‌شده باید جداگانه و با تصمیم محصولی انجام شود.
4. سیاست scope برای temporary_access: مقدار NULL هرگز به‌صورت ضمنی tenant-wide نیست. تا زمان وجود command امن با کنترل approver مطابق SEC-414، write wrapper باید scope_id خالی را با INVALID_ARGUMENT رد کند. دسترسی tenant-wide فقط با یک data_scope صریح از نوع tenant و approval معتبر (برای allow) قابل تعریف است؛ Resolver فعلی scope خالی را fail-closed نگه می‌دارد.

## 9. مرز انتشار

این قرارداد مبنای پیاده‌سازی نسخه ۱ است. چهار Migration مربوط به hardening Resolver و API خواندنی در تاریخ 2026-11-20 روی پروژه اصلی اجرا و در تاریخچه ثبت شده‌اند. دو RPC عمومی فقط برای نقش authenticated قابل اجرا هستند؛ schemaهای داخلی expose نشده‌اند و هیچ write API در این نسخه منتشر نشده است.

صفحه `org-structure-readonly.html` از context و snapshot استفاده می‌کند. آزمون بدون نشست روی دیتابیس اصلی با AUTH_REQUIRED انجام شده است؛ آزمون مثبت با نشست واقعی مدیر، scopeهای چندشرکتی و سناریوهای deny هنوز باید از مرورگر احراز هویت‌شده تکمیل شود. جزئیات در `HR_SOFT_Supabase_Deployment_Report_v0.3.md` ثبت شده است.
