# HR-SOFT — تحلیل دامنه امنیت و مدیریت کاربران نسخه 0.1

- مبنا: سند مادر تحلیل و مشخصات نرم‌افزار منابع انسانی، نسخه 1.0
- وضعیت: پیش‌نویس تحلیلی؛ مدل نهایی پس از مشاهده صفحه‌های باقی‌مانده تثبیت می‌شود.
- دامنه: کاربر، گروه کاربری، عضویت چندگانه، احراز هویت، محدودیت‌ها و گزارش‌های امنیتی.

### 1.2 محدودیت شواهد

سند مادر جزئیات permissionها، actionها، دامنه داده‌ای، ترتیب تقدم گروه‌ها، معنای دقیق گروه پیش‌فرض، ساختار کلیدها و رفتار تنظیمات کاربر را مشخص نمی‌کند. بنابراین این سند برای این موارد تصمیم قطعی نمی‌سازد.

## 2. واژگان دامنه

- **کاربر:** حساب ورود به نرم‌افزار؛ از «شخص» و «پرسنل» متمایز است.
- **گروه کاربری:** مجموعه‌ای برای سازمان‌دهی دسترسی در یک سیستم/ماژول.
- **عضویت گروه:** رابطه کاربر با یک گروه؛ کاربر می‌تواند چند عضویت هم‌زمان داشته باشد.
- **گروه پیش‌فرض:** گروهی که در رابط مرجع امکان تعیین آن مشاهده شده؛ کاربرد دقیق آن هنوز روشن نیست.
- **نوع احراز هویت:** عادی، Active Directory یا هر دو.
- **محدودیت IP:** قاعده محدودسازی دسترسی بر اساس محدوده IP؛ جزئیات هنوز نامشخص است.
- **سایر کاربران مجاز:** قابلیت مشاهده‌شده در صفحه کاربر؛ ماهیت رابطه و دامنه اثر آن نیازمند بررسی است.
- **فهرست کلیدها:** قابلیت مشاهده‌شده؛ نوع کلید، مالکیت، چرخه عمر و کاربرد آن نامشخص است.

## 3. مدل مفهومی پیشنهادی و موقت

این مدل صرفاً اسکلت قابل توسعه است و تا مشاهده صفحه‌های مجوز گروه و تنظیمات کاربر، نهایی نیست.

| موجودیت پیشنهادی | نقش در مدل | وضعیت تصمیم |
|---|---|---|
| `users` | حساب ورود، نام کاربری و وضعیت حساب | اصل وجود قطعی؛ فیلدهای کامل نیازمند استخراج |
| `user_auth_methods` | روش یا روش‌های احراز هویت کاربر | موجودیت پیشنهادی؛ جزئیات پیاده‌سازی نامشخص |
| `user_groups` | گروه کاربری با عنوان، سیستم و وضعیت فعال | مبتنی بر فیلدهای مشاهده‌شده |
| `user_group_memberships` | اتصال چندبه‌چند کاربر و گروه | چندعضویتی تأییدشده |
| `user_login_policies` | محدودیت زمانی یا سایر قواعد ورود | فقط پس از استخراج جزئیات |
| `user_ip_rules` | محدوده‌های IP مجاز/ممنوع | وجود قابلیت مشاهده‌شده؛ ساختار نامشخص |
| `user_authorized_peers` | بازنمایی موقت قابلیت «سایر کاربران مجاز» | نام و رابطه نهایی نیازمند بررسی |
| `user_keys` | بازنمایی موقت فهرست کلیدها | ماهیت کلیدها نیازمند بررسی |
| `user_security_events` | رخدادهای امنیتی مانند تغییر وضعیت حساب | پیشنهاد طراحی؛ باید با گزارش‌های واقعی تطبیق داده شود |
| `user_access_reports` | داده/نمای گزارش دسترسی کاربران | ساختار گزارش نیازمند مشاهده |
| `user_login_reports` | داده/نمای گزارش ورود کاربران | ساختار گزارش نیازمند مشاهده |

## 4. قواعدی که می‌توان اکنون تثبیت کرد

1. حساب کاربری را با شخص یا پرونده پرسنلی یکی نکنید؛ سند مرجع برای «شخص» و «کاربر» صفحه‌های جداگانه دارد.
2. عضویت کاربر در گروه باید چندبه‌چند باشد؛ محدودکردن هر کاربر به یک گروه با شواهد فعلی ناسازگار است.
3. گروه باید به سیستم/ماژول مربوط باشد؛ فهرست سیستم‌های مشاهده‌شده باید در تحلیل دامنه حفظ شود.
4. وضعیت فعال گروه و وضعیت حساب کاربر دو مفهوم جدا هستند.
5. نوع احراز هویت را از مجوزهای کاربردی جدا نگه دارید؛ روش ورود به‌تنهایی نباید معادل مجوز دسترسی تلقی شود.
6. رخدادهای ورود و دسترسی را از وضعیت جاری حساب جدا نگه دارید تا گزارش تاریخی قابل نگهداری باشد.
7. تا روشن‌شدن رفتار واقعی، گروه پیش‌فرض را به‌عنوان «گروه یگانه کاربر» یا تنها منبع مجوزها تفسیر نکنید.

## 5. تصمیم‌های باز و شواهد لازم

| شناسه | پرسش باز | شواهد لازم برای تصمیم |
|---|---|---|
| SEC-01 | مجوزهای هر گروه در چه سطحی تعریف می‌شوند؟ | صفحه جزئیات گروه و فهرست permission/action |
| SEC-02 | عضویت در چند گروه چگونه ترکیب می‌شود؟ | نمونه کاربر با دو گروه و نتیجه دسترسی مؤثر |
| SEC-03 | آیا منع دسترسی بر اجازه تقدم دارد؟ | تنظیمات تعارض یا آزمون رفتاری کنترل‌شده |
| SEC-04 | دامنه دسترسی داده‌ای چیست؟ | فیلدهای شرکت/سازمان/واحد یا محدوده رکورد در مجوزها |
| SEC-05 | گروه پیش‌فرض چه کاربردی دارد؟ | توضیح رابط، رفتار هنگام ورود و رفتار افزودن گروه |
| SEC-06 | محدودیت زمانی ورود در چه سطحی اعمال می‌شود؟ | فیلدها، بازه‌ها، منطقه زمانی و پیام خطا |
| SEC-07 | مجوز محدوده IP چگونه تعریف می‌شود؟ | ورودی‌های IP/CIDR، سیاست پیش‌فرض و رفتار عدم تطبیق |
| SEC-08 | «سایر کاربران مجاز» چه رابطه‌ای می‌سازد؟ | فیلدها، عملیات و اثر واقعی بر دسترسی |
| SEC-09 | «فهرست کلیدها» چه نوع کلیدهایی است؟ | نام فیلدها، ایجاد/ابطال/انقضا و کاربرد |
| SEC-10 | تنظیمات کاربر شامل چه گزینه‌هایی است؟ | مشاهده کامل صفحه و آزمون اثر هر گزینه |
| SEC-11 | گزارش دسترسی چه رویدادها و فیلترهایی دارد؟ | ستون‌ها، فیلترها، خروجی و جزئیات رکورد |
| SEC-12 | گزارش ورود چه داده‌هایی ثبت می‌کند؟ | ستون‌ها، موفق/ناموفق، زمان، IP و فیلترها در صورت وجود |

## 6. برنامه بررسی صفحه «تنظیمات کاربر»

هنگام دسترسی به سامانه مرجع، فقط مشاهده انجام شود و هیچ تنظیمی ذخیره یا تغییر داده نشود. برای هر گزینه این اطلاعات ثبت شود:

1. عنوان دقیق صفحه و گروه‌بندی گزینه‌ها؛
2. نام و نوع کنترل هر فیلد (متن، انتخابی، کلید روشن/خاموش، تاریخ/زمان و غیره)؛
3. مقدار پیش‌فرض و مقادیر قابل انتخاب؛
4. دامنه اعمال: فقط کاربر جاری، همه کاربران، یک گروه یا یک سیستم؛
5. امکان تغییر توسط کاربر عادی یا فقط مدیر؛
6. اثر قابل مشاهده گزینه و پیام‌های اعتبارسنجی؛
7. ارتباط احتمالی با گروه پیش‌فرض، احراز هویت، محدودیت ورود و مجوزها.

**خروجی لازم:** جدول فیلدها + جدول عملیات + فهرست ابهام‌ها. تا پیش از مشاهده، هیچ گزینه‌ای به‌عنوان قابلیت Admino فرض نشود.

## 7. ترتیب پیاده‌سازی پیشنهادی پس از تکمیل تحلیل

1. تکمیل واژگان و موجودیت‌های کاربر، گروه و عضویت چندگانه.
2. استخراج و تصویب مدل مجوزها و دامنه داده‌ای.
3. تعریف سیاست احراز هویت و کنترل حساب.
4. تعریف محدودیت‌های زمانی و IP.
5. تعریف «سایر کاربران مجاز» و کلیدها پس از روشن‌شدن معنای دقیق.
6. طراحی ثبت رخداد و گزارش‌ها بر اساس ستون‌ها و رفتار واقعی صفحات.
7. طراحی آزمون‌های دسترسی مؤثر برای کاربر تک‌گروهی و چندگروهی، حساب مسدود، محدودیت زمانی و IP.

## 8. نتیجه

از اطلاعات فعلی می‌توان با اطمینان، چندعضویتی کاربران در گروه‌ها، ارتباط گروه با سیستم، سه روش احراز هویت و وجود برخی کنترل‌های حساب را در مدل پایه لحاظ کرد. اما تعیین ماتریس مجوز، الگوریتم ترکیب گروه‌ها، دامنه دسترسی و رفتار تنظیمات کاربر بدون مشاهده صفحات مربوطه قابل دفاع نیست.
