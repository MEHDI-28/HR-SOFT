# HR-SOFT — طراحی موتور دسترسی مؤثر
## نسخه ۲.۱ | مدل تصمیم‌گیری مجوز و محدوده داده

وضعیت: طراحی فنی؛ آماده تبدیل به تابع‌های SQL پس از آزمون fixtureها. هیچ تابعی روی Supabase اجرا نشده است.

## ۱. هدف

یک نقطه تصمیم‌گیری مرکزی برای همه درخواست‌های دسترسی بسازیم تا منطق مجوز در صفحات مختلف برنامه تکرار یا دور زده نشود.

تابع منطقی پیشنهادی:
`hr_security.can_access(system_key, permission_key, operation, tenant_id, company_id, org_unit_id, personnel_record_id)`

خروجی فقط boolean است؛ ثبت رویداد ممیزی برای عملیات حساس باید در لایه سرویس/رویه کنترل‌شده و در همان تراکنش انجام شود، نه با تکیه بر کلاینت.

## ۲. ورودی‌های معتبر

- هویت: فقط از `auth.uid()`؛ هرگز از شناسه کاربر ارسالی کلاینت اعتماد نشود.
- Tenant: از `hr_security.app_users` فعال استخراج شود؛ `tenant_id` ارسالی باید با آن برابر باشد.
- System و Permission: با کلیدهای ثابت کاتالوگ resolve شوند.
- Operation: یکی از `view`, `add`, `edit`, `delete`, `download`, `approve`, `execute`.
- محدوده رکورد: از رکورد واقعی پایگاه داده استخراج یا با روابط FK اعتبارسنجی شود؛ به `company_id`, `org_unit_id`, `personnel_record_id` ارسالی کلاینت به‌تنهایی اعتماد نشود.

## ۳. ترتیب تصمیم‌گیری (الزامی)

1. حساب احراز هویت‌شده باید به یک `app_users` فعال متصل باشد؛ در غیر این صورت رد.
2. Tenant رکورد هدف باید با Tenant حساب فعال یکسان باشد؛ در غیر این صورت رد.
3. گروه باید فعال، عضویت فعال و در بازه اعتبار باشد.
4. گروه باید متعلق به همان System باشد.
5. محدوده داده باید با رکورد هدف منطبق باشد.
6. برای عملیات `add/edit/delete`، پرچم متناظر مجوز باید فعال باشد.
7. برای مشاهده عادی، قاعده فعلی کاربر «مشاهده مجاز به‌صورت پیش‌فرض در محدوده سیستم/داده مجاز» رعایت شود؛ این به معنی مشاهده همه شرکت‌ها یا همه Tenantها نیست.
8. برای اطلاعات حساس، مشاهده پیش‌فرض اعمال نمی‌شود؛ permission key مستقل مانند `sensitive.identity.view` یا `sensitive.bank.view` الزامی است.
9. برای دانلود، permission key مستقل مانند `sensitive.documents.download` الزامی است.
10. اگر هر گروه فعال برای همان عملیات/محدوده قاعده `deny` داشته باشد، نتیجه نهایی رد است؛ deny بر allow سایر گروه‌ها مقدم است.
11. اگر هیچ allow معتبر با محدوده منطبق وجود نداشته باشد، رد (default deny).
12. دسترسی موقت فقط در بازه `starts_at <= now() < ends_at` اعتبار دارد و از همان اولویت deny پیروی می‌کند.

## ۴. منطق محدوده داده

| نوع Scope | منطق انطباق |
|---|---|
| tenant | هر رکورد متعلق به همان Tenant |
| company | رکورد متعلق به شرکت مشخص |
| org_unit | واحد مشخص؛ در صورت `include_descendants=true` تمام زیرواحدها |
| personnel | پرونده پرسنلی مشخص |

برای `org_unit` باید مسیر سلسله‌مراتب از واحد هدف به سمت والدها پیمایش شود. چرخه درخت باید در سطح constraint/trigger ممنوع شود تا تابع scope وارد حلقه بی‌پایان نشود.

Scopeهای گروه‌های مختلف با هم ترکیب می‌شوند، اما deny منطبق در هر گروه نتیجه را رد می‌کند. نبود Scope منطبق، اجازه دسترسی نمی‌دهد.

## ۵. تفاوت مجوز عملیاتی و مجوز حساس

- مجوزهای عادی: گروه‌های سیستم، scope و پرچم add/edit/delete.
- مشاهده عادی: طبق تصمیم قبلی، در محدوده داده مجاز پیش‌فرض است.
- مشاهده حساس: کلید مجوز مستقل و صریح.
- دانلود حساس: کلید مجوز مستقل از مشاهده.
- اصلاح سوابق گذشته: کلید مجوز ویژه مانند `history.correct`.
- اجرای درخواست ظرفیت: مجوز جدا از تأیید درخواست، مانند `capacity.execute`.
- مشاهده تاریخچه مجوزها: فقط `permission_history.view` که به نقش/کاربران مجاز «مدیر سیستم» اعطا می‌شود.

## ۶. مواردی که نباید انجام شود

- اعتماد به role یا tenant داخل `user_metadata`.
- استفاده از `service_role` در مرورگر.
- تصمیم‌گیری صرفاً در React/UI بدون RLS/Backend.
- ساخت policy با `USING (true)` روی جدول‌های HR.
- فرض اینکه عضویت در یک گروه به معنی دسترسی به تمام شرکت‌هاست.
- فرض اینکه مجوز مشاهده، مجوز دانلود فایل را هم می‌دهد.
- حذف یا بازنویسی audit برای اصلاح اشتباهات.
- اجرای function با `SECURITY DEFINER` بدون `search_path=''`, کنترل هویت و محدودیت EXECUTE.

## ۷. طرح policy بر اساس خانواده داده

| خانواده | شرط پایه | شرط افزوده |
|---|---|---|
| tenant/company | tenant فعال | scope و مجوز سیستم |
| people/personnel | tenant فعال | scope شرکت/واحد/پرسنل |
| organization | tenant فعال | scope سازمانی |
| assignments | tenant فعال | scope + مجوز مشاهده/ثبت/ویرایش |
| security groups | tenant فعال | مجوز مدیریت امنیت |
| permission history | tenant فعال | مدیر سیستم + permission_history.view |
| workflow | tenant فعال | درخواست‌کننده، مسئول گام یا مجوز مدیریت گردش کار |
| capacity requests | tenant فعال | نقش درخواست‌کننده/تأییدکننده/مدیر سیستم |
| notifications | tenant فعال | فقط دریافت‌کننده |
| files | tenant فعال | دسترسی به رکورد مالک + مجوز فایل |
| sensitive | tenant فعال | مجوز صریح مشاهده/ویرایش/دانلود + audit |

این جدول یک policy matrix مفهومی است، نه SQL نهایی. پیش از تولید SQL، برای هر جدول عملیات مجاز و رابطه مالک/مسئول/Scope باید جداگانه تعیین شود.

## ۸. آزمون‌های تکمیلی موتور دسترسی

- کاربر در دو گروه با دو scope مختلف: دسترسی فقط به اجتماع scopeهای allow.
- deny در گروه اول و allow در گروه دوم برای همان رکورد: رد.
- deny در واحد والد و allow در زیرواحد: رد، مگر اینکه قواعد کسب‌وکار به‌طور صریح deny را محدود کنند؛ تصمیم فعلی deny مطلق است.
- دسترسی موقت همراه با عضویت گروه: فقط در بازه زمانی مجاز.
- رکورد با شرکت/واحد ناسازگار در ورودی: تابع باید رکورد را از DB resolve کند یا رد کند.
- درخواست view عادی در scope مجاز: مجاز.
- درخواست view اطلاعات بانکی بدون کلید حساس: رد.
- درخواست download بدون مجوز download مستقل: رد.
- درخواست execute ظرفیت با وجود approve ولی بدون execute: رد.
- حساب blocked: رد حتی اگر گروه و scope فعال باشند.
