# HR-SOFT — امنیت RLS و Tenant Isolation
## نسخه ۲.۰ | بسته طراحی مرحله سوم

وضعیت: طراحی و فایل SQL پیش‌نویس؛ هنوز روی Supabase یا دیتابیس دیگری اجرا نشده است.

## ۱. نتیجه مهم بررسی مستندات رسمی Supabase

- RLS کنترل ردیف‌هاست و با GRANTهای PostgreSQL تکمیل می‌شود؛ وجود RLS به‌تنهایی جایگزین محدودسازی مجوزهای جدول/تابع نیست. <https://supabase.com/docs/guides/api/securing-your-api>
- هر جدول در schema در معرض Data API باید RLS داشته باشد؛ جدول بدون policy در حالت RLS فعال به‌صورت پیش‌فرض دسترسی ردیفی نمی‌دهد. <https://supabase.com/docs/guides/database/postgres/row-level-security>
- توابع `SECURITY DEFINER` باید `search_path` امن داشته باشند، دسترسی EXECUTE آن‌ها محدود شود و داخل تابع مالکیت/هویت درخواست بررسی شود. <https://supabase.com/docs/guides/database/functions>
- فایل‌های Storage نیز با RLS روی `storage.objects` کنترل می‌شوند؛ bucket خصوصی و سیاست‌های مجزای خواندن/نوشتن/دانلود لازم است. <https://supabase.com/docs/guides/storage/security/access-control>
- جداول schema مربوط به Storage باید فقط از API رسمی Storage تغییر کنند؛ دستکاری مستقیم آن‌ها توصیه نمی‌شود. <https://supabase.com/docs/guides/storage/schema/design>

## ۲. تصمیم معماری امنیت

### مرزها
1. `tenant_id` در تمام جداول کسب‌وکاری اجباری است.
2. روابط داخلی با FK مرکب `(tenant_id, id)` مانع اتصال رکوردهای متعلق به Tenantهای متفاوت می‌شود.
3. schemaهای `hr_core`, `hr_org`, `hr_security`, `hr_audit`, `hr_workflow`, `hr_files`, `hr_notify`, `hr_sensitive` داخلی می‌مانند و نباید به‌صورت مستقیم در فهرست exposed schemas قرار گیرند.
4. سطح API باید از طریق schema اختصاصی `api` و view/functionهای محدودشده ارائه شود؛ اگر معماری backend واسط انتخاب شود، جداول داخلی اصلاً از Data API ارائه نمی‌شوند.
5. هیچ مجوزی از `user_metadata` قابل ویرایش کاربر استخراج نمی‌شود.
6. اصل دسترسی: default deny؛ عدم وجود مجوز به معنی عدم دسترسی است.

### تابع‌های پایه
- `hr_security.current_app_user_id()` شناسه حساب داخلی متناظر با `auth.uid()` را برمی‌گرداند.
- `hr_security.current_tenant_id()` Tenant حساب فعال را برمی‌گرداند.
- این دو تابع در SQL پیوست به‌صورت `SECURITY DEFINER` با `search_path=''` و نام‌گذاری کامل اشیا تعریف شده‌اند.
- اجرای تابع برای `public` و `anon` لغو و فقط برای `authenticated` مجاز شده است.
- مالک تابع باید نقش مورد اعتماد و تحت کنترل باشد؛ این توابع نباید به مالک/نقشی واگذار شوند که کاربر عادی بتواند آن را تغییر دهد.

## ۳. وضعیت سیاست‌ها در SQL ضمیمه

فایل `HR_SOFT_RLS_Lockdown_v0.1.sql`:
- RLS را روی همه جدول‌های تعریف‌شده در دو بسته SQL قبلی فعال می‌کند.
- مجوزهای گسترده جدول را از `public`, `anon`, `authenticated` لغو می‌کند.
- فقط خواندن Tenant خود، پروفایل حساب خود و کاتالوگ‌های عمومی سیستم/مجوز را باز می‌گذارد.
- برای داده‌های شرکت، شخص، پرسنل، سازمان، گروه، گردش کار، فایل، ممیزی و اطلاعات حساس هنوز هیچ policy دسترسی ایجاد نمی‌کند؛ در نتیجه این داده‌ها برای کاربر authenticated نیز بسته می‌مانند.
- این یک مرحله قفل ایمن است، نه سیاست نهایی بهره‌برداری.

## ۵. طرح آزمون اجرایی

این آزمون‌ها باید پس از ایجاد محیط staging با دو Tenant ساختگی اجرا شوند:
- Tenant A / شرکت A / کاربر A
- Tenant B / شرکت B / کاربر B

برای هر جدول و هر عملیات `SELECT`, `INSERT`, `UPDATE`, `DELETE`:
1. آزمون مجاز در محدوده کاربر.
2. آزمون رد برای رکورد متعلق به Tenant دیگر.
3. آزمون رد برای عملیات فاقد مجوز.
4. آزمون رد برای scope خارج از محدوده.
5. آزمون deny-priority با دو گروه متناقض.
6. آزمون زمان‌مند قبل، حین و بعد از بازه اعتبار.

ابزار مورد نظر: `supabase test db` با pgTAP، به‌علاوه آزمون API/Storage در محیط staging. تا زمانی که fixtureهای دو Tenant و کاربران آزمایشی ایجاد نشده‌اند، خروجی تست نباید «موفق» اعلام شود.

## ۶. ریسک‌ها و کارهای باز

- سیاست‌های scope هنوز به توابع و جدول‌های scope متصل نشده‌اند.
- قواعد دسترسی حساس برای هر فیلد/نوع داده و رویداد ممیزی مشاهده/دانلود باید تکمیل شوند.
- Storage policy بدون شناسه bucket و الگوی object path واقعی نهایی نمی‌شود.
- دسترسی سرویس backend و service role باید محدود، ثبت‌شده و فقط سمت سرور باشد.
- دسترسی مستقیم کلاینت به جداول داخلی توصیه نمی‌شود.
- اگر viewها در API ساخته شوند، رفتار RLS آن‌ها باید با `security_invoker` و مجوزهای underlying بررسی شود.
- هیچ ادعایی درباره وضعیت واقعی پروژه Supabase HR-SOFT وجود ندارد؛ ابزار فهرست پروژه‌ها در این نوبت خطای داخلی داد.

## ۸. گام‌های بعدی بدون نیاز به تصمیم جدید
1. ساخت توابع محاسبه مجوز مؤثر (allow/deny) و محدوده داده.
2. طراحی policy برای هر جدول بر اساس مجوز و scope.
3. طراحی دسترسی حساس view/download و audit event.
4. طراحی Storage path و policy با مسیر Tenant/record/version.
5. نوشتن تست‌های pgTAP با fixtureهای ساختگی.
6. بررسی SQLها از نظر وابستگی، ترتیب migration و rollback.
7. بازگشت به مرور صفحه پرسنلی Admino وقتی محتوای واقعی آن از مرورگر قابل خواندن باشد.
